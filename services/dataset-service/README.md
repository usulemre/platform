# Dataset Service (`dataset_service`) — Data Platform + Dataset Service

> **Two layers, both implemented, interfaces only** — no ingestion adapters, storage engine,
> database, API, external connector, or persistence:
>
> - **Phase 2.0 — Data Platform** (`dataset_service.*`): the authoritative dataset _domain_ —
>   models, catalog, registry, metadata, schema, versioning, lifecycle, lineage, discovery, access
>   policies, and validation integration.
> - **Phase 2.2 — Dataset Service** (`dataset_service.application.*`): the _application/orchestration_
>   layer on top of the Data Platform — registration workflows, validation coordination, version
>   management, discovery/search, access/classification/ownership coordination, and service events.

## Purpose

Realize the **Data Platform Layer** (Architecture V2 §5.8): certified, point-in-time-correct,
provenance-bearing data as the only foundation research may stand on. All historical reads are
served through the **As-Of Gateway** (`core_domain.dataset.AsOfGateway`, fail-closed without an
`as_of`, PIT-1); raw/uncertified/OOS data is never exposed (DI-1). This is the **first production
platform module** and builds on the Phase-1 foundations rather than duplicating them.

## What is here (Phase 2.0)

16 modules, each a subpackage with its own `README.md`:
`model` · `metadata` · `schema` · `versioning` · `lifecycle` · `catalog` · `registry` · `discovery`
· `lineage` · `policies` · `access_control` · `validation_integration` · `events` · `errors` ·
`repositories` · `services`.

## What is here (Phase 2.2 — application layer: `dataset_service.application`)

The **Dataset Service** application/orchestration layer — 12 modules, each with its own `README.md`:
`registration` · `discovery` · `search` · `metadata` · `version_management` ·
`validation_coordination` · `access_management` · `classification` · `ownership` · `lifecycle` ·
`events` · `errors`.

- **Operates on top of the Data Platform** (uses `dataset_service.*` as the canonical data domain)
  and **uses the Validation Foundation** (`platform_validation`) for validation orchestration —
  certification/leakage/survivorship remain the deterministic engine's decision (DI-1, AI-2).
- **Operational lifecycle coordinated:** registration → validation → publication → deprecation →
  archival, plus **version promotion** and **governed dataset replacement** (supersede-and-deprecate,
  never mutate — CP-2/DEPR-2).
- **Service events** (`application.events`): `DatasetRegistrationRequested`, `DatasetRegistered`,
  `DatasetValidationRequested`, `DatasetValidated`, `DatasetPublished`, `DatasetVersionPromoted`,
  `DatasetDeprecated`, `DatasetArchived` (the `*Requested` signals drive workflows).
- **Self-contained:** the application layer does not modify the Phase-2.0 domain; it is imported as
  `dataset_service.application`. Verified: application code has **no** storage/db/ingestion/connector/
  API imports — only stdlib, `core_domain.shared`, `platform_validation`, and the Data Platform domain.
- Generated by [`tools/scaffolding/generate_dataset_service.sh`](../../tools/scaffolding/generate_dataset_service.sh)
  (idempotent, auditable), distinct from the Phase-2.0 generator.

- **Canonical models** (`model`): `Dataset` (catalog aggregate, reuses `core_domain.AggregateRoot`),
  `DatasetVersion`, `DatasetIdentifier`, `DatasetStatus`, `DatasetClassification`,
  `DatasetOwnership`, `DatasetMetadata`, `DatasetSchema`, `DatasetLineage`, `DatasetAccessPolicy`.
- **Lifecycle**: `PROPOSED → REGISTERED → VALIDATING → VALIDATED → PUBLISHED → DEPRECATED →
ARCHIVED`, with version-upgrade/schema-evolution re-entering `VALIDATING`; skips forbidden
  (fail-closed); publication requires a passed certification gate (DI-1).
- **Domain events** (`events`): `DatasetRegistered`, `DatasetValidated`, `DatasetPublished`,
  `DatasetDeprecated`, `DatasetArchived`, `DatasetVersionCreated`, `DatasetSchemaUpdated`,
  `DatasetOwnershipTransferred` (subclass `core_domain.shared.DomainEvent`).

## How it reuses the foundations (no duplication)

- **`core_domain`** — reuses `shared` primitives (`AggregateRoot`, `EntityId`, `Version`,
  `ContentAddress`, `Provenance`, `LineageRef`, `DomainEvent`, `DomainError`) and the `dataset`
  context (`AsOfGateway`, `CertificationService`, `CertificationStatus`) for the PIT read path and
  data-quality certification.
- **`platform_contracts`** — `SchemaVersion` for schema/version identity.
- **`platform_validation`** — `validation_integration` bridges to the structural Validation
  Foundation (`ValidationContext`, `ValidationReport`); **statistical certification stays in the
  deterministic engine** (DI-1, AI-2) — the platform never certifies data with an LLM.

## Boundary rules (verified)

- **Deterministic:** no ambient time/RNG; `as_of`/`since` are supplied data (CS-3).
- **Technology-independent, no infrastructure:** a scan confirms **no** database/storage/broker/
  connector/HTTP/file-IO imports (`sqlalchemy`/`arcticdb`/`duckdb`/`kafka`/`boto3`/`s3`/`requests`/
  `fastapi`/`os`/`open`…). Ingestion adapters and storage engines plug in **behind** these interfaces.
- **Immutable & auditable:** every model/record/event is a `frozen` dataclass (runtime
  `FrozenInstanceError`); registry/repositories are append-only; metadata carries owner/provenance.
- **Point-in-time & lineage:** `PointInTimePolicy` mandates as-of + survivorship safety;
  `LineageGraph.invalidate_downstream` supports source-defect propagation (CP-6, DP-2).
- **Security:** `access_control` is default-deny, need-to-know; crown-jewel data restricted (SEC-2).
- **Compiles and imports cleanly** across all four foundation packages; dependency direction is
  service → packages (no cycles).
